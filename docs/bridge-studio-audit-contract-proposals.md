# Bridge Studio 감사 계약 협의안

두 제안은 별개로 승인할 수 있다. 현재 Controller의 직접 근거 수집, 독립 감사, Apply 권한은 현행 경로를 사용한다.

## A. Judge·Critic 판정 읽기

개별 판정은 검증된 `requests[].reportRef`로 저장된다. 목록의 역할·상태와 종합 판정은 현재 조회 가능하다. 공용 `evidence.get`의 조회 대상은 실행의 증거 ID다.

제안은 현재 대시보드 인증을 통과한 읽기 경로에서 **처리 완료된, 검증된 역할별 판정**만 조회하는 것이다. 서버가 요청의 실행 ID·후보 ID·manifest·역할과 artifact 해시를 검증하고 정규화된 판정, 이유, 근거 참조만 반환한다. 클라이언트가 임의 artifact 경로 또는 해시를 넘겨 열 수 없도록 한다. 이전 후보 판정은 이력에서 명시적으로 선택한다. 전송 중, 오래된 manifest, 손상/누락, 해당 역할 미검토를 서로 구분한다.

- 같은 후보·manifest의 두 역할이 서로 다른 판정을 냄 → 역할별 결과와 각각의 근거를 보이며 Controller의 합산 Gate는 유지한다.
- 다른 실행, 처리 전 보고서, 해시 불일치 또는 접근 불가 → 원문은 제공하지 않고 확인 불가 사유를 표시한다.
- 개인정보가 포함된 비공개 응답 원문 → 기존 비공개 저장 경계를 유지한다.

### 최소 구현 범위

1. 기존 대시보드 인증을 적용하는 읽기 전용 `GET /api/review-assessments`를 사용한다. 입력은 현재 실행·후보·확정 감사 식별자다. Controller가 확정 감사의 저장 경계에서 manifest와 역할별 요청을 선택한다. 임의 artifact 경로·해시와 과거 후보는 입력 범위 밖이다.
2. 역할별 요청이 `PROCESSED`인지, 확정 manifest/후보/패치 및 역할·요구사항 버전과 함께 귀속되는지 먼저 검사한다. 같은 manifest에 반대 판정이 있더라도 각각 보존한다. `ArtifactStore`의 무결성 조회와 기존 report 검증을 재사용한다. 역할당 확정 입력을 유일하게 결정할 수 없으면 해당 역할을 조회 불가로 표시한다.
3. 정규화된 요구사항 ID·판정·근거 ID와 조회 상태만 반환한다. 보고서·응답 원문, 프롬프트, 비공개 artifact 및 ACK 복구는 기존 경계를 유지한다. 두 역할의 확정 입력을 복원할 수 없으면 `UNAVAILABLE`을 반환한다. 기존 종합 판정은 그대로 읽는다.
4. 격리 검증에서 성공·다른 Run·다른 후보·다른 manifest·역할 위조·해시 손상·미처리 요청을 각각 시험한다. 반복 조회 전후에 상태·버전·이벤트·명령 영수증과 Apply 권한이 같음을 비교한다. 승인·재검토·ACK 명령은 전송하지 않는다.
5. 승인된 경우에만 감사 화면에 개별 역할 열을 붙인다. 서로 다른 결과와 결과가 아직 없는 경우를 구분하고, 역할 조회를 종합 Gate의 조건으로 삼지 않는다.

## B. Critic 요청의 Worker 조사 및 회신

현재 Controller는 코드·기존 증거를 직접 조회하거나 등록된 검증만 실행한다. 이 범위로 답할 수 없는 요청에 별도 승인 범위의 **읽기 전용 조사**를 추가하는 제안이다.

Controller가 Critic 요청을 `runId`, `candidateId`, `auditManifestHash`, `patchHash`, `requestId`, `requestItemId`에 결박한다. Worker에는 열람 범위와 결과 형식을 구조화해 전달한다. 조사 입력과 출력은 별도 위치에 두고, Worker는 후보 작업 트리에 변경을 남길 수 없는 환경에서 동작해야 한다. Controller는 시작과 종료에 후보 식별과 패치 해시를 재검증한다. 결과는 자료·출처·조사 한계로 저장하고 독립 판정에 필요한 근거 유형을 자동 충족하지 않는다. 승인된 계획을 벗어나는 명세 변경·실행은 현재 USER_DECISION 경로로 분기한다.

GUI에는 동일 요청의 접수, 조사 중, 회신 검증 중, Critic 전달, 독립 판정과 실패 사유를 증거로 연결한다. 중단이나 통신 불확실 상태는 회신을 확정하지 않고 복구 화면에 표시한다. 기존 결과 또는 전송의 귀속을 입증하지 못하면 자동 재전송하지 않는다. 새 유효 근거로 manifest가 달라질 때는 현행 독립 재검토 규칙을 따르며, 이전 판정을 새 manifest에 승격하지 않는다.

- 권한 범위에 있는 요청 → 한 번 조사하고 같은 후보에 결박한 회신을 넘긴 뒤 Critic이 따로 판단한다.
- 조사 중 후보 변경 또는 잘못된 회신 → 회신을 거절하고 이전 후보·증거 이력을 보존한다.
- Worker 실패, ACK 불확실 또는 복구 후 재접수 → 전송과 회신의 실측 상태가 표시되고 사용자 확인이나 검증된 같은 요청의 복구 경로만 허용한다.

재시작 시 요청의 영수증과 동일한 조사 식별자의 검증 상태를 다시 읽는다. 결과가 없으면 실패 또는 보류를 표시하고, 결과가 있더라도 그 회신의 귀속과 해시를 확인하기 전에는 Critic에게 전달하지 않는다. 후보 편집, 새로운 명령 실행, 조사 자료 외부 송신, 별도 사실 인정을 보장할 근거가 필요한 경우는 각각 승인 범위에서 결정한다. Controller가 답할 수 있는 기존 `CODE`·`EVIDENCE`·등록 `VERIFY` 요청은 현행 처리에 그대로 남긴다.

구현 전 각각의 공개 데이터 범위, 실패 후 재개 조건, 운영 권한을 결정해야 한다.
